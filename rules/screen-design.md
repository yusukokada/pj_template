# 業務画面の作り方

## 1. 画面は最初から業務の単位で作る
テーブル単位の画面は管理画面（`/admin/`、データ定義書から自動で生成する器）に任せ、成果物にしない。業務画面は「誰が・何の業務で・何を判断するか」の単位で作る（例：案件の状況、月次の締め、ベンダーの評価）。
**Why:** テーブル単位の画面を並べても、業務の流れに沿わず使えないと指摘された。
**How to apply:** 画面を作る前に、画面ごとに「使う人・場面・判断・使うテーブル」を一覧にしてユーザーに確かめる。

## 2. 判断を求める画面には、問い・診断・原因・推奨を置く
指標やデータを並べるだけの画面にしない。判断を求める画面には次を置く。
- 問い（何を判断するか）・判断する人・期限
- 診断（いまの状態。判定とその理由）
- 原因（どのデータからそう言えるか。明細へのリンク）
- 見通し・選択肢・推奨とその理由

**Why:** 可視化だけの画面は「何が問題で、どうすべきか」が分からないと指摘された。
**How to apply:** 画面の一番上に「対応が必要な件数と理由」を出し、その下に一覧、明細の順にする（手本：`app/work/sample.py`）。

## 3. 計算は画面から分ける
判定・集計は `app/work/` の関数に分け（例：`sample.project_status()`）、画面（views）は表示だけにする。導出のテーブルも同じ関数で作る（例：`sample.build_weekly()`）。
**Why:** 計算を画面に書くと、同じ指標が画面ごとに違う値になる。

## 4. 閾値はマスタから読む
判定の境界・目標値はデータ定義書の指標の定義から読む。コードに数値を直書きしない（手本の sample.py は、マスタが無いので例外として直書きしている）。

## 5. 画面の文言も説明資料と同じルールで書く
見出し・ラベル・ボタン・判定の文・注記まで、[説明資料の文章](business-doc-writing.md) の 3・4b・4c を当てはめる。動詞で終えず体言止め、主語・目的語を明示、あいまい語・比喩を使わない（例：「根拠を見る」→「根拠の明細」）。
**How to apply:** `python app/tools/audit_wording.py` で洗い出してから見直す。

## 6. 数値の表示を揃える
金額は百万円・小数2桁（単価は円のまま）。工数は人日・小数1桁。テンプレートでは `{% load fmt %}` の `mil`・`num` を使う。

## 7. 確かめ方
- `python app/tools/smoke.py`：全画面が開くか
- `python app/tools/audit_wording.py`：文言
- 見た目：`python manage.py runserver` で開くか、テストクライアントで HTML を書き出してブラウザで撮る
- 業務画面には、意味の通るダミーデータ（`seed_<業務>` のコマンド）を作る。乱数のデータでは判定が出ず、画面の確認にならない
