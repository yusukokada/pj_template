# データモデルの考え方

## 1. 事象 → 課題 → To-Be像 → データモデル → ルール の順で進める
①起きている事象を洗い出して課題を導く → ②課題が解けた状態（To-Be像）を判断とデータの言葉で描く → ③To-Be像を実現するにはどのデータが要るか（データモデル）→ ④細かいルール（閾値・運用・自動化の範囲）。①②が終わる前に③④へ進まない。
**Why:** データモデルから書き始めると、何を解くためのデータかが曖昧なまま項目が増え、ユーザーに①へ戻すよう指摘された。データモデルは課題だけでは決まらず、To-Be像を実現するためのデータとして決まる。
**How to apply:** ①では、AI がユーザーの気づいていない事象・場面の候補を出し、ユーザーが「起きている／起きていない」を答えて積み上げる。上からの目指す姿（トップダウン）も仮置きし、事象（ボトムアップ）と突き合わせる。②の書き方は下の「To-Be像の書き方」。

## 1b. To-Be像の書き方
- 「どの判断を、どのデータで、どう自動化するか」の形で書く。判断の材料は自動で算出し、見直し・中止・廃止の候補は自動で抽出し、人は抽出された候補について判断する
- 課題の裏返し（「〜できない」を「〜できる」にしただけ）にしない。ほかの領域のデータを使うことで初めて得られる判断を軸にする
- 体制・会議体の見直しで解く形にしない。判断の基準をデータの側に持たせる
- 現場に新たに求める作業を明記し、既存の記録の様式の変更か、初回だけの作業に抑える
- 実現したいことはユーザーが示す。AI は聞き出し、候補を出すまで

**Why:** 課題の裏返しの To-Be像は、何のデータが要るかを示さず、データモデルの範囲が決まらない。人の役割を定義し直す To-Be像は、運用で崩れる。

## 2. 人は素の事実だけを入力し、判断・指標は計算で出す
- 素の事実だけを入力する（日付・工数・金額・状態）。判断の値（遅れている・良い悪い）を人に入力させない
- 導出の値は「導出」の層のテーブルにし、記録・マスタから計算で作る
- 時系列はスナップショット（基準日ごとの導出の行）で持つ
- 共通のキーとマスタで、領域をまたいでつなぐ
- 同じ事実を2か所に入力させない

**Why:** 人が判断の値を入れると、人や案件で基準が揃わず、入力の手間も増える。事実だけを入れ、判断は計算で出せば、全件を同じ基準で比べられる。
**How to apply:** 新しい項目を足すたびに「これは事実か、判断か」「どこかで既に入力していないか」を確かめる。`definition.py check` は、記録・マスタに「計算」の項目があると気づきとして出す。

## 3. テーブル単位 → 項目単位の順で詰める
まずテーブルの一覧（1行の単位・正とする所・管理するデータ・用途）で受け皿が揃っているかを決め、その後に項目を詰める。最初から正規化しすぎない。
**Why:** 項目から始めると全体の抜けが見えず、テーブルの切り方を後から変えると項目を全部作り直すことになる。

## 4. 各テーブルに「1行の単位」と「正とする所」を書く
- 1行の単位：例「タスク1つ」「案件×基準日」。複合キーの組み合わせと一致させる
- 正とする所：そのデータの元のシステム・台帳（人事システム、このシステム、など）

**Why:** 1行の単位が曖昧だと集計が二重になる。正とする所が無いと、どちらの値を信じるかで揉める。

## 5. 製品に寄せることを目的にしない
導入する製品（ServiceNow など）の標準テーブルは参考として対応づけるだけにし、構造は業務の判断に要る形を優先する。製品に項目を足す前に、まず標準の項目と比べる。
**Why:** 製品に合わせると、解きたい課題に要るデータが落ちる。
**How to apply:** ただし、製品を動かすのに要るデータ（ロール・会計期間など）は、判断に使わなくても定義書に入れる（導入時に止まらないように）。区別できる ID の付け方にする。

## 6. 閾値・目標値はデータにする
判定の境界（遅延とみなす日数、超過とみなす倍率）や目標値は、指標の定義のマスタに持つ。コードに数値を直書きしない。
**Why:** 業務で閾値を変えるたびにプログラムを直すことになり、どの値で判定したかも残らない。

## 7. 行を消さない
マスタの廃止は有効フラグで外す。記録は消さずに状態で表す。
**Why:** 過去の記録が参照している行を消すと、過去の集計が変わる。

## 定義書の作り方
- 正は docs/ の `【データ定義書】…_vX.Y.xlsx`
- 直すときは `python doc_tools/definition.py dump` で JSON にし、JSON を直し、`build` で新しい版を作る（体裁が毎回同じになる）
- 型・層・取得の一覧は定義書の 00_凡例 と `doc_tools/definition.py` の TYPES・LAYERS
- 区分の選択肢は 91_コード値案 に「コード：表示名」で書く
