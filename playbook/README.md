# 進め方の手順書

事象と課題から To-Be像を描き、それを実現するデータモデル（データ定義書）を作り、試作アプリの業務画面と説明資料にするまでの手順。AI はこの順で進め、各段階の「確かめ方」に合格し「ユーザーに確かめること」の答えをもらってから次へ進む。

| 段階 | 作るもの | 確かめ方 | 次へ進む条件 |
|---|---|---|---|
| [1. 事象と課題](1-issues.md) | 目指す姿（仮置き）と、事象・課題・解きたい判断の一覧 | ユーザーが事象を「起きている」と答えた件数 | 課題と判断の一覧にユーザーが合意 |
| [2. To-Be像](2-tobe.md) | 領域別の To-Be像（どの判断を、どのデータで、どう自動化するか） | すべての課題がどれかの To-Be像で解ける、目指す姿と突き合わせた | To-Be像にユーザーが合意 |
| [3. データモデル](3-data-model.md) | データ定義書 v0.x（テーブル一覧 → 項目） | `definition.py check` で誤り0件、To-Be像の判断がすべてデータで出せる | テーブル一覧と1行の単位にユーザーが合意 |
| [4. 試作アプリ（業務画面）](4-prototype.md) | 定義書から生成した器の上に作る業務画面と、意味の通るダミーデータ | `check_all.py` が OK、画面の撮影 | 画面ごとの判断が画面から読めるとユーザーが確認 |
| [5. 資料](5-documents.md) | 説明資料（pptx） | PNG で全ページ、文章ルールの点検 | ユーザーの確認 |

## 段階をまたぐ約束
- 段階を飛ばさない。とくに、1（事象と課題）と 2（To-Be像）が終わる前に 3（データモデル）を書き始めない（[rules/data-model.md](../rules/data-model.md) の1）
- 後の段階で前の段階の不足が見つかったら、前の段階の成果物（定義書など）を直して版を上げ、作り直す。アプリのコードだけで辻褄を合わせない
- 段階ごとに、決まったことを `rules/project/` に書く
- 毎回の作業の終わりに `python check_all.py` を流し、結果をそのまま報告する

## 見つかった不足の扱い
画面や計算を作ると、データ定義書の不足（項目がない、1行の単位が合わない、閾値の置き場所がない）が見つかる。これは試作の一番の成果なので、隠さずに一覧にする。
- 試作の中では仮置き（コードに直書きなど）で進めてよいが、仮置きした場所にコメントを残す
- 一覧をユーザーに見せ、定義書に反映するかを決めてもらう
- 反映したら、定義書の版を上げ → `app/tools/rebuild.py` → 仮置きを外す

## どの段階でも添える一言
各段階の依頼の例は、各段階のファイルの「依頼の例」にある。どの段階でも、次の一言を添える。
- 「作業の前に rules/README.md と関係するルールを読んで」
- 「終わったら check_all.py の結果をそのまま報告して」
- 指摘をしたときは「今の指摘を、理由つきで rules/ に書いて」
