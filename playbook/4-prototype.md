# 4. 試作アプリ（業務画面）

## 目的
2 の To-Be像の判断が、データから実際に出せることを、業務の画面で示す。ルールは [rules/screen-design.md](../rules/screen-design.md)。

作るのは最初から**業務の単位の画面**。テーブル単位の画面（`/admin/` の管理画面）は、データ定義書から自動でできる器で、成果物ではない。ITマネジメント高度化では最初にテーブル単位の画面を作り、「業務の単位で画面を扱うべき」と指摘されて作り直した。

## 作るもの
- 画面の一覧（画面ごとに：使う人・場面・判断・使うテーブル）
- 画面ごとに：計算の関数（`app/work/<業務>.py`）、画面（`views_<業務>.py`・`templates/work/<業務>*.html`）、URL（`urls.py`）、メニュー（`nav.py`）
- 意味の通るダミーデータ（`app/work/management/commands/seed_<業務>.py`、`tools/rebuild.py` の SEEDS に足す）

手本は `app/work/sample.py`・`views_sample.py`・`seed_sample.py`（サンプルの定義書のときだけ動く）。自分の画面ができたら手本は消す。

## 進め方
1. **器を作る**（ユーザーの確認を待たずに進めてよい）：docs/ のデータ定義書を1つにし、`app/work/nav.py` の SYSTEM_NAME を変え、`cd app` → `python tools/rebuild.py`（モデル・管理画面・乱数のダミーデータ）→ `python tools/smoke.py`
2. 画面の一覧を作り、ユーザーに確かめる
3. 1画面ずつ：意味の通るダミーデータ → 計算の関数 → 画面 の順に作る。判定が実際に出るように、ダミーデータに「注意」になる行を意図して入れる
4. 計算に要るデータが定義書に無ければ、仮置きで進め、不足の一覧に入れる（[手順書の README](README.md) の「見つかった不足の扱い」）
5. 画面を撮影してユーザーに見せる

## 器の生成の決まり（tools/gen_models.py）
- 領域 → アプリ（02_領域のアプリ名）。テーブル → モデル `T<テーブルID>`。項目名は日本語のまま項目の名前になる
- PK が1つならそれが主キー、複数なら組み合わせの一意制約
- 参照先があれば外部キー。区分は 91_コード値案 の選択肢（DB にはコード、画面には表示名）
- 導出のテーブルは管理画面で編集できない（計算で作るため）
- 生成したファイルは直接直さない。定義書を直して作り直す

## うまくいかないとき
- `definition.py check` の誤り → 定義書を直す
- 必須の参照が循環している（seed が止まる）→ どちらかの参照を任意にするか、テーブルの切り方を見直す（定義書の不足として一覧に入れる）
- アプリ名が Python の名前と衝突する（例：ast）→ 02_領域のアプリ名を変える

## 確かめ方
- `python check_all.py --no-office`：定義書の点検・器の作り直し・全画面・文言（引数つきの画面は `urls.py` の SMOKE_URLS に足す）
- 撮影：テストクライアントで HTML を書き出し、ブラウザ（Edge・Chrome のヘッドレス）で PNG にして見る。または runserver で開く
- 判定の数が、ダミーデータで意図した数と合う

## ユーザーに確かめること
- 画面の一覧
- 判定の閾値（仮置きの値）
- 画面から判断が読めるか

## 次へ進む条件
画面ごとの判断が画面から読めるとユーザーが確かめた。不足の一覧の扱いが決まった。

## 依頼の例
〈〉は差し替える部分。

> 「定義書から器を作ったうえで、〈業務〉で〈誰〉が〈何〉を判断する画面を作りたい。まず画面一覧（使う人・場面・判断）を出して。画面には問い・診断・原因・推奨を置き、判定が出るダミーデータも作って。定義書に無いデータは仮置きして一覧にして」

伝えること：
- 判断する人と、何を判断するか
- 画面一覧を先に出させること
- 定義書の不足を一覧にさせること
